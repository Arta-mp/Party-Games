# پلن ساخت اپ بازی‌های گروهی (Party Games)

Nov 21, 2026 · @Arta Mortezapour

## ۱. خلاصه و اهداف

یک وب‌اپ سبک (PWA) فارسی برای بازی‌های گروهی می‌سازیم که روی موبایل مثل اپ نصب می‌شود و روی GitHub Pages رایگان میزبانی می‌شود. هر کاربر فقط یک نام کاربری دارد، لابی می‌سازد یا با کد وارد لابی می‌شود و یکی از بازی‌ها را با دوستانش بازی می‌کند.

**اهداف نسخه‌ی اول (MVP):**

- بدون ثبت‌نام، رمز یا دیتابیس کاربر. فقط نام کاربری که در دستگاه ذخیره می‌شود.

- ساخت لابی با کد ۴ حرفی، لینک دعوت و QR کد.

- دو حالت بازی: **آنلاین** (هر نفر با گوشی خودش) و **یک‌گوشی / Pass & Play** (گوشی دست‌به‌دست می‌شود و به اینترنت نیاز ندارد).

- بازی‌ها در «خانواده»‌ها دسته‌بندی می‌شوند و هر خانواده چند مود دارد، مثلاً خانواده‌ی جاسوس شامل جاسوس کلاسیک، آندرکاور و آفتاب‌پرست است.

- برای هر بازی تا حد امکان نقش، کلمه و پک محتوای کاستوم قابل تعریف است.

- کد کاملاً اپن‌سورس و پابلیک روی گیت‌هاب.

**خارج از محدوده‌ی MVP:** حساب کاربری، رتبه‌بندی جهانی، چت متنی، اپ نیتیو در استورها.

## ۲. تصمیم کلیدی: هاستینگ و ارتباط آنلاین

GitHub Pages فقط فایل استاتیک سرو می‌کند و بک‌اند، WebSocket یا دیتابیس ندارد. پس برای لابی آنلاین باید یک لایه‌ی ارتباطی رایگان جداگانه انتخاب کنیم.

**راه‌حل پیشنهادی: معماری Host-Authoritative با Transport قابل تعویض**

- گوشی سازنده‌ی لابی (Host) خودش سرور بازی است: قوانین را اجرا می‌کند، نقش‌ها را پخش می‌کند و State را نگه می‌دارد.

- بقیه‌ی بازیکنان فقط اکشن می‌فرستند و «نمای شخصی» خودشان را دریافت می‌کنند (هر کس فقط نقش خودش را می‌بیند).

- ارتباط پشت یک اینترفیس Transport است تا هر وقت سرویس بلاک یا کند شد، فقط یک آداپتور عوض شود.

- حالت Pass & Play از همان موتور با یک LocalTransport استفاده می‌کند و هیچ شبکه‌ای لازم ندارد.

| گزینه‌ی Transport                                | نوع                                                  | نیاز به ثبت‌نام/کلید | مزیت                    | ریسک                                                           |
| ------------------------------------------------ | ---------------------------------------------------- | -------------------- | ----------------------- | -------------------------------------------------------------- |
| [Trystero](https://github.com/dmotz/trystero)    | P2P (WebRTC) با سیگنالینگ عمومی (Nostr/MQTT/Torrent) | خیر                  | صفر سرور، کاملاً استاتیک | پشت NAT اپراتورهای موبایل ممکن است وصل نشود (TURN لازم می‌شود) |
| Supabase Realtime (Broadcast + Presence)         | کلاینت-سرور                                          | بله، پلن رایگان      | پایدار، Presence آماده  | پروژه‌ی بی‌استفاده پس از مدتی متوقف می‌شود                     |
| Cloudflare Worker + Durable Object (یا PartyKit) | WebSocket روی اج                                     | بله، پلن رایگان      | سریع، کنترل کامل        | کمی کد سرور لازم دارد                                          |
| Firebase Realtime DB                             | کلاینت-سرور                                          | بله                  | مستندات زیاد            | سرویس‌های گوگل از ایران معمولاً مشکل دارند؛ توصیه نمی‌شود       |

**تصمیم:** شروع با TrysteroTransport چون هیچ تنظیمی نمی‌خواهد. آداپتور دوم (SupabaseTransport یا Cloudflare) به‌عنوان پشتیبان در فاز ۲ ساخته می‌شود. قبل از هر چیز، یک دموی کوچک اتصال را با اینترنت همراه و وای‌فای دوستانتان در ایران تست کنید.

## ۴. معماری

هر بازی یک ماژول پلاگینی است که منطق خالص (pure reducer) دارد و از شبکه هیچ چیزی نمی‌داند. با این روش، یک مود جدید فقط یک پوشه اضافه می‌کند و به هسته دست نمی‌زند.

### ۴.۱ اینترفیس بازی

```ts
// src/core/engine/types.ts
export interface GameModule<Config, State, Action, View> {
  id: string; // 'spy.classic'
  family: FamilyId; // 'hidden-word'
  meta: {
    nameFa: string;
    minPlayers: number;
    maxPlayers: number;
    supportsPassAndPlay: boolean;
    supportsCustomRoles: boolean;
  };
  configSchema: z.ZodType<Config>; // تنظیمات مود (تایمر، تعداد جاسوس، پک کلمه)
  defaultConfig: Config;
  setup(players: Player[], config: Config, rng: Rng): State;
  reduce(state: State, action: Action, actor: PlayerId, ctx: Ctx): State; // pure
  viewFor(state: State, viewer: PlayerId | 'public'): View; // اسرار را مخفی می‌کند
  result(state: State): GameResult | null;
  screens: { Setup: FC; Play: FC<{ view: View }>; Results: FC };
}
```

### ۴.۲ اینترفیس ارتباط

```ts
// src/core/net/transport.ts
export interface Transport {
  host(roomCode: string): Promise<void>;
  join(roomCode: string, hello: Hello): Promise<void>;
  toHost(msg: ClientMsg): void;
  toPeer(peerId: string, msg: HostMsg): void;
  broadcast(msg: HostMsg): void;
  on(event: 'message' | 'peer-join' | 'peer-leave', cb: Handler): Unsubscribe;
  leave(): void;
}
// پیاده‌سازی‌ها: TrysteroTransport, LocalTransport (Pass & Play), SupabaseTransport (بعداً)

type ClientMsg =
  { t: 'hello'; name: string; deviceId: string } | { t: 'action'; action: unknown; seq: number };
type HostMsg =
  | { t: 'lobby'; lobby: LobbyState }
  | { t: 'view'; gameId: string; view: unknown; rev: number }
  | { t: 'error'; code: string };
```

### ۴.۳ مسیر یک اکشن (Trace)

1.  بازیکن دکمه‌ی «رأی به علی» را می‌زند ← dispatch({ type: 'vote', target: 'p3' }).

2.  کلاینت اکشن را با transport.toHost({ t: 'action', ... }) می‌فرستد.

3.  هاست با Zod اعتبارسنجی می‌کند و state = game.reduce(state, action, actor, ctx) را اجرا می‌کند.

4.  هاست برای هر بازیکن viewFor(state, id) می‌سازد و با toPeer می‌فرستد.

5.  کلاینت‌ها view جدید را در Zustand می‌گذارند و UI رندر می‌شود.

6.  خود هاست هم از همین مسیر (Loopback) استفاده می‌کند تا کد دوباره نوشته نشود.

قوانین مهم: RNG باید seed‌دار باشد تا تست‌پذیر باشد. تایمرها با endsAt (زمان مطلق هاست) ارسال می‌شوند، نه با tick. اسرار هرگز در broadcast فرستاده نمی‌شوند.

## ۵. هویت کاربر و سیستم لابی

هویت فقط یک نام کاربری و یک deviceId تصادفی است که در localStorage ذخیره می‌شود. هیچ سرور احراز هویتی وجود ندارد.

### ۵.۱ نام کاربری

- اولین بار صفحه‌ی «اسمت چیه؟» نمایش داده می‌شود: ۲ تا ۱۶ کاراکتر، فارسی و انگلیسی، بدون فاصله‌ی اضافه.

- یک آواتار رنگی از روی hash نام ساخته می‌شود (بدون آپلود عکس).

- یکتایی نام فقط داخل هر لابی چک می‌شود. اگر تکراری بود، هاست می‌پرسد یا یک عدد اضافه می‌کند.

- از منوی تنظیمات قابل تغییر است.

### ۵.۲ چرخه‌ی لابی

1.  **ساخت:** کاربر «ساخت لابی» را می‌زند ← کد ۴ حرفی بدون حروف مشابه (مثل K7QM، بدون 0/O و 1/I) ساخته می‌شود و او هاست است.

2.  **دعوت:** نمایش کد بزرگ، QR کد، دکمه‌ی اشتراک لینک (#/join/K7QM) با Web Share API.

3.  **ورود:** بازیکنان وارد می‌شوند و لیست با Presence زنده آپدیت می‌شود. هاست می‌تواند کیک کند یا لابی را قفل کند.

4.  **انتخاب بازی:** هاست خانواده و مود را انتخاب و تنظیم می‌کند. مودهایی که با تعداد فعلی نفرات سازگار نیستند غیرفعال‌اند.

5.  **آماده‌باش:** هر نفر «آماده‌ام» می‌زند و هاست بازی را شروع می‌کند.

6.  **پایان دور:** نتایج، جدول امتیاز جلسه، و دکمه‌ی «دور بعد» یا «برگشت به لابی». امتیازها تا بسته شدن لابی می‌مانند.

### ۵.۳ قطع و وصل و انتقال هاست

- بازیکن قطع‌شده با همان deviceId برمی‌گردد و جایگاهش حفظ می‌شود (۶۰ ثانیه مهلت).

- هاست State را هر بار در localStorage ذخیره می‌کند تا رفرش صفحه بازی را نابود نکند.

- اگر هاست برنگشت، در لابی قدیمی‌ترین بازیکن هاست می‌شود. وسط بازی بازی متوقف می‌شود و هاست می‌تواند بازی را «انتقال» دهد (Snapshot به هاست جدید).

### ۵.۴ حالت Pass & Play

هاست نام همه را وارد می‌کند. برای نمایش نقش، صفحه‌ی «گوشی را به علی بده» نمایش داده می‌شود، بعد نگه داشتن برای دیدن نقش و در آخر «مخفی کن و بده به نفر بعد».

بازی‌ها در ۵ خانواده دسته‌بندی می‌شوند. هر خانواده یک «هسته‌ی مشترک» دارد و مودها فقط تفاوت‌هایشان را پیاده می‌کنند. ستون «فاز» به رودمپ بخش ۹ اشاره دارد.

## ۷. سیستم نقش و محتوای کاستوم

نقش کاستوم یک **داده‌ی JSON** است که از قطعه‌های آماده (primitive) ساخته می‌شود، نه کد اجرایی. پس بدون eval امن است، با Zod اعتبارسنجی می‌شود و با یک لینک قابل اشتراک است.

### ۷.۱ سه سطح کاستوم‌سازی

| سطح             | برای کدام خانواده   | چه چیزی قابل تعریف است                                       |
| --------------- | ------------------- | ------------------------------------------------------------ |
| پک محتوا        | همه                 | مکان‌ها، کلمه‌ها، جفت‌کلمه‌ها، کلمات ممنوعه، طیف‌ها، سؤال‌ها |
| نقش اطلاعاتی    | کلمه‌ی مخفی (جاسوس) | نقش چه رازی می‌بیند، چه کسانی را می‌شناسد، شرط بردش          |
| نقش توانایی‌دار | مافیا / گرگینه      | تیم، اکشن شب، تعداد دفعات، اولویت، ویژگی‌های غیرفعال         |

### ۷.۲ نقش اطلاعاتی (خانواده‌ی جاسوس)

هر نقش با سه سؤال تعریف می‌شود: چه می‌بیند، چه کسی را می‌شناسد، چطور می‌برد.

```jsonc
{
  "id": "witness",
  "nameFa": "شاهد",
  "team": "citizens",
  "sees": "secret", // secret | similar | none | category
  "knows": ["spy"], // نقش‌هایی که هویتشان را می‌داند
  "win": "team",
  "onEliminated": "spyGuessesWitness",
  "count": { "min": 0, "max": 1 },
  "descriptionFa": "جاسوس را می‌شناسد ولی نباید لو برود",
}
```

با همین مدل، جاسوس (sees: none)، نفوذی آندرکاور (sees: similar) و آقای سفید هم فقط داده هستند و کد جداگانه نمی‌خواهند.

### ۷.۳ نقش توانایی‌دار (خانواده‌ی مافیا)

```jsonc
{
  "id": "sniper",
  "nameFa": "تک‌تیرانداز",
  "team": "citizens",
  "night": {
    "action": "kill", // kill | protect | investigate | block | silence | reveal | swap | convert
    "target": "other", // self | other | any | teammate
    "uses": 1, // یک بار در کل بازی
    "priority": 40, // ترتیب حل اکشن‌ها
    "fromNight": 2,
  },
  "passive": ["appearsInnocent"], // bulletproof | appearsInnocent | revengeKill | ...
  "knowsTeammates": false,
  "onWrongKill": "selfDies",
}
```

**ترتیب حل اکشن‌های شب (پیش‌فرض):** block (۱۰) ← protect (۲۰) ← kill (۳۰–۴۰) ← investigate (۵۰) ← reveal (۶۰). هاست می‌تواند اولویت هر نقش را تغییر دهد.

### ۷.۴ ویرایشگر و اشتراک

- ویرایشگر فرمی مرحله‌به‌مرحله: نام و آیکون ← تیم ← توانایی ← شرط برد ← پیش‌نمایش کارت نقش.

- اعتبارسنجی ترکیب نقش‌ها قبل از شروع: مثلاً «تیم مافیا نباید از نصف بازیکنان بیشتر باشد».

- نمایش یک «نشانگر تعادل» ساده با جمع وزن نقش‌ها (هر نقش یک عدد وزن دارد).

- ذخیره در localStorage، خروجی JSON و **کد اشتراک** (JSON فشرده با lz-string داخل لینک \#/import/...).

- وقتی بازی شروع می‌شود، هاست نقش‌ها و پک‌های کاستوم را به بقیه می‌فرستد و نصب جداگانه لازم نیست.

- پک‌های پیشنهادی دوستان می‌توانند با Pull Request به content/packs/ اضافه شوند.

## ۸. UI/UX، فارسی و اسکیل‌های Claude Code

اولویت طراحی این است که اپ وسط جمع با یک دست و بدون توضیح قابل استفاده باشد.

### ۸.۱ اصول طراحی

- **Mobile-first و تم تیره به‌عنوان پیش‌فرض** (مهمانی‌ها معمولاً شب است)، با تم روشن اختیاری.

- هر خانواده یک رنگ تاکیدی ثابت دارد (مثلاً جاسوس بنفش، مافیا قرمز، حدس کلمه نارنجی) و بقیه‌ی UI خنثی است.

- دکمه‌ها حداقل ۴۸ پیکسل، اکشن اصلی پایین صفحه در محدوده‌ی شست.

- نمایش نقش با کارت برگشته: «نگه دار تا ببینی»، با رها کردن دوباره مخفی می‌شود تا بغل‌دستی نبیند.

- تایمر دایره‌ای بزرگ، لرزش (navigator.vibrate) و صدای کوتاه در ۱۰ ثانیه‌ی آخر. صدا قابل قطع است.

- Screen Wake Lock در طول بازی تا صفحه خاموش نشود.

- انیمیشن‌ها زیر ۳۰۰ میلی‌ثانیه و احترام به prefers-reduced-motion.

- هر بازی یک صفحه‌ی «چطور بازی کنیم؟» ۳ مرحله‌ای دارد که از لابی قابل باز شدن است.

### ۸.۲ فارسی و RTL

- \<html dir="rtl" lang="fa"\> و فقط کلاس‌های منطقی Tailwind (ms-\*، me-\*، ps-\*، start-\*)، نه ml/mr.

- اعداد با Intl.NumberFormat('fa-IR')، ولی کد لابی همیشه لاتین و با dir="ltr".

- همه‌ی متن‌ها در src/i18n/fa.ts تا انگلیسی بعداً راحت اضافه شود.

- فونت Vazirmatn به‌صورت self-host (بدون وابستگی به Google Fonts).

- نرمال‌سازی ورودی‌ها برای مقایسه (ی/ي، ک/ك، نیم‌فاصله، اعراب) برای اسم فامیل و «فقط یکی» ضروری است.

### ۸.۳ اسکیل‌های Claude Code که باید استفاده شوند

| اسکیل                                   | کی استفاده شود                                     | نکته                                                     |
| --------------------------------------- | -------------------------------------------------- | -------------------------------------------------------- |
| ui-ux-pro-max                           | قبل از ساخت Design System و هر صفحه‌ی جدید         | اسکیل کامیونیتی است؛ اول نصب بودنش را با /skills چک کنید |
| frontend-design (پلاگین رسمی Anthropic) | انتخاب جهت بصری، تایپوگرافی، جلوگیری از ظاهر قالبی | برای صفحه‌ی خانه و کارت‌های بازی                         |
| webapp-testing (Playwright)             | بعد از هر فاز، برای اسکرین‌شات و تست چندتب         | شبیه‌سازی ۴ بازیکن در ۴ تب                               |

## ۱۱. تست، ریسک‌ها و ایده‌های آینده

بزرگ‌ترین ریسک اتصال آنلاین در شبکه‌های ایران است؛ به همین دلیل Pass & Play اول ساخته می‌شود و Transport قابل تعویض است.

### ۱۱.۱ استراتژی تست

- **واحد (Vitest):** هر reducer با seed ثابت؛ مثلاً «با ۶ نفر و ۲ جاسوس دقیقاً ۲ نفر مکان را نمی‌بینند».

- **امنیت اسرار:** تست خودکار که خروجی viewFor هر بازیکن اسرار دیگران را نداشته باشد.

- **اسکیما:** همه‌ی پک‌های content/packs/ در CI با Zod چک می‌شوند.

- **E2E (Playwright):** ۴ تب هم‌زمان یک دست کامل بازی می‌کنند، با اسکرین‌شات موبایل در عرض ۳۹۰ پیکسل.

- **تست واقعی:** بعد از هر فاز یک شب بازی با دوستان و ثبت باگ‌ها به‌صورت GitHub Issue.
